## 开篇：先把「全自动」这两个字拆开

大部分教程会告诉你「装个 Bot，销售全自动」。这句话是错的，而且错得很贵。

真正跑通的团队自己写得很清楚：

> 凡是没法清晰定义判断标准的决策，我们要求人工审核；凡是 Bot 要起草面向客户的沟通内容，也要求人工审核。

所以这篇教程的分工是这样的：

| 环节 | 能不能自动 | 谁做 |
|---|---|---|
| 客户调研 | ✅ 全自动 | Bot |
| 会前简报 | ✅ 全自动（定时跑） | Bot |
| 读会议记录 | ✅ 全自动 | Bot |
| 更新 CRM 字段 | ⚠️ 半自动（先出预览，人确认） | Bot 提议 + 人点确认 |
| 起草跟进邮件 | ⚠️ 只能起草 | Bot 写，人发 |
| 报折扣 / 非标条款 | ❌ 不能自动 | 人工审批（权限单独设限） |
| 客户沟通 | ❌ 不能自动 | 人 |

记住这张表。凡是说「连邮件都能自动发」的教程，要么没用过，要么在卖课。

全自动的部分，是把一个人从每天 3 小时的杂活里拿出来。这才是真正的收益，而且它不靠吹。

## 第 0 步：先确认你能不能建共享 Bot

| 你的情况 | 能不能用 |
|---|---|
| X Premium / Super / Ultra 订阅 | ✅ Grok Bot 包含在内（Plus 和 Free 不含） |
| Cursor 付费个人计划 / Cursor Teams | ✅ 包含 |
| SuperGrok / SuperGrok Plus / SuperGrok Heavy / X Premium+ | ✅ 可以绑定 |
| 自己买一个 Grok Business 席位 | ✅ 可以 |
| 企业 | 需要管理员在 Cursor dashboard 里开启；企业版才有审计日志、Team Secrets、网络控制 |

Shared Bots（团队共享）只在 Teams / Enterprise 计划公开测试（2026-09-28 起）。

注意：套餐明细来自第三方整理，下单前以官方页面为准。

一个硬限制先记住：共享 Bot 必须跑在云端。你本地电脑上跑的 Bot 没办法共享。

## 第 1 步：建第一个 Bot

官方文档（2026-10 版）的步骤：

1. Grok Bot 侧边栏点 + → Create a Bot，起个名字
2. 告诉它「要帮团队做什么」——一句话就够
3. 跟着它的引导步骤配置 apps、secrets、skills、files
4. 点聊天顶部的 Bot 名字 → Share → Who has access → 选团队或邀请特定人，给 Collaborator 或 Manager 权限
5. 同事在 + > Browse shared Bots 里找到它 → Add
6. 团队用 Slack 的话，再点 Bring to your team's Slack → Connect

> 看不到 Browse shared Bots → 你不在 Cursor team 里，或者 App 需要更新。

第 2 步那句话，是最重要的一句话。

❌ 「帮我处理销售相关的事情」  
（太宽 → Bot 什么都做不好）

✅ 「帮我负责的 12 个账号做会前准备和会后更新，所有对外内容只起草不发送」  
（有范围、有边界）

## 第 2 步：喂 Context——三层知识

一个共享 Bot 有四个组成部分：Context（上下文）、Plugins（插件）、Credentials（凭证）、Memories（记忆）。

其中 Context 是所有人最不当回事、但影响最大的一层：

> 一个共享 Bot 有没有用，取决于你喂了它什么材料。一份品牌指南或一份内部手册，对输出质量的提升，比一句聪明的提示词大得多。

按三层喂：

| 层 | 放什么 | 举例 |
|---|---|---|
| 第 1 层：产品与品牌 | 不常变 | 产品线说明、定价规则、品牌口吻、不能说的话 |
| 第 2 层：流程与规则 | 季度更新 | 什么情况算商机、什么情况必须上报、折扣权限边界 |
| 第 3 层：客户与账号 | 每天变 | 客户档案、历史往来、组织架构、竞争对手 |

别把第 3 层塞进文件里。第 3 层应该从 Salesforce 之类的系统实时读，而不是你手动维护一份会过期的文档。

## 第 3 步：接 Plugins——让它够得着你的系统

Plugins 是 Bot 连接到应用的方式。xAI 点名的例子：Salesforce、Notion、GitHub。

能接插件的，就别用凭证。凭证（Credentials / Secrets）是没有插件时的兜底方案——直接调第三方 API。

**最小可用组合（销售）**

| 插件 | 用途 | 优先级 |
|---|---|---|
| Salesforce | 读账号/商机、写更新 | 🥇 必须 |
| Slack | 发晨报、收请求 | 🥇 必须 |
| Gmail / Outlook | 读往来邮件 | 🥈 强烈建议 |
| 会议记录工具 | 读通话记录（原文用 Gong） | 🥈 强烈建议 |
| Notion | 内部文档、话术库 | 🥉 可选 |

**中国团队怎么办**

原文用的是 Salesforce + CPQ + Ironclad + Gong + Slack 这套外企栈。换成国内的，方法论完全一样：

| 原文组件 | 国内替代 |
|---|---|
| Salesforce | 纷享销客 / 销售易 / 简道云 |
| Slack | 飞书 / 企业微信 / 钉钉 |
| Gong 通话记录 | 飞书妙记 / 通义听悟 |
| Ironclad 合同 | e签宝 / 法大大 |
| Notion | 飞书文档 / 语雀 |

没有插件怎么办？用 Credentials 直接调 API。这也是国内工具的主要路径。

## 第 4 步：把动作固化成 Skill（这一步决定成败）

Skill 是什么：一套可复用的任务指令。Routine 是「什么时候跑」，Skill 是「跑什么」。

顺序千万别搞反：

> 先把一个任务做可靠，再存成 Skill，最后才谈自动化。

先自动化一个你自己都跑不利索的流程，只会更快地产出垃圾。

下面是四个可以直接抄的 Skill。把 `{{}}` 里的内容换成你自己的。

### Skill 1｜会前简报

**Skill 1｜会前简报（可直接复制）**

```
【任务】为 {{客户名}} 生成会前简报。
【输出结构】严格按这 5 段，每段不超过 5 行：
1. 这家公司最近 30 天发生了什么（只列事实，每条标来源链接）
2. 我们和它的历史往来（从 Salesforce 读）
3. 上次通话的三个关键点（从会议记录读）
4. 这次会议他们最可能关心的两个问题
5. 我该准备的三个问题
【禁止】
- 不要给建议
- 不要预测成交概率
- 不要写没有来源的信息。没查到就写「未查到」
【输出】直接发给我，不要反问我确认。
```

### Skill 2｜会后 CRM 更新

**Skill 2｜会后 CRM 更新（可直接复制）**

```
【任务】读取 {{会议}} 的记录，更新 Salesforce 里对应的商机。
【步骤】
1. 提取：客户提的需求、异议、下一步动作、负责人、时间点
2. 生成预览表：字段名 | 现在的值 | 准备改成
3. 等我确认后，再写入
【硬边界】
- 金额字段：只读，永不修改
- 成交日期：只读，永不修改
- 不要创建新商机
- 不确定的信息，宁可不写
```

### Skill 3｜跟进邮件草稿

**Skill 3｜跟进邮件草稿（可直接复制）**

```
【任务】起草会后跟进邮件。
【输入】会议记录 + Salesforce 商机信息
【要求】
- 语言与客户往来语言一致
- 不超过 150 字
- 只写三件事：确认理解 / 下一步 / 谁在什么时候做什么
- 不提价格，不提折扣
【输出】草稿 + 一句话说明你这么写的理由
【硬规则】永远不要发送。只起草，等人审核。
```

这条「永远不要发送」，就是原文里那条规矩的落地：客户沟通必须有人的判断。

### Skill 4｜折扣前先自查

**Skill 4｜折扣前先自查（可直接复制）**

```
【任务】我准备给 {{客户}} 报价 {{折扣}}，先帮我查。
【检查】
1. 这个折扣在我的权限范围内吗（读《折扣权限表》）
2. 需要谁批
3. 同类客户的历史成交折扣区间（从 Salesforce 取，只读）
【输出】一张表：项目 | 结论 | 依据
【禁止】不要替我提交审批。只告诉我该找谁。
```

> 原文那句值得贴墙上：销售代表不能用报价 Bot 批准自己的折扣。

## 第 5 步：用 Routine 让它自己跑

Routine 是「什么时候跑」。触发器类型：

| 触发器 | 用途 |
|---|---|
| 定时（带时区） | 每天早上 8:30 发晨报 |
| Slack 消息 | 有人在频道里 @它 |
| 邮件 | 客户来信触发 |
| GitHub / Linear / Sentry / PagerDuty 事件 | 技术团队场景 |
| Webhook | 自定义（⚠️ 第三方观察到的用法，官方文档未列） |

报道的限制值：单个 Bot 最多 50 个 routine，保留 20 条运行记录（xAI 官方未公布，以实测为准）

**最值得自动化的第一个 Routine**

```
每天早上 8:30（北京时间） 为我负责的每个账号生成一段晨报，发到 Slack 的 #sales-accounts：
- 昨天发生了什么变化（公司新闻 / 客户邮件 / 相关 Slack 讨论）
- 这个账号今天最该做的一件事
- 一句话写清为什么是这件事
【禁止】没有变化就写「无变化」，不要硬凑内容。
```

最后那句「不要硬凑内容」，是防 AI 通病的关键。不加这句，你每天早上会收到 12 条废话。

## 第 6 步：教一遍就会（教它学，而不是写提示词）

Grok Bot 有个别的产品少见的能力：你做一遍，它看着，然后接管这条路。

对着屏幕演示一遍你的操作流程，让它把路径记下来，存成 Skill。

两个实操要点：

- 有说法是单次演示录制约 10 分钟上限（官方未公布，需实测）
- 演示的时候别聊天。专心把流程走对，它学的是你的动作，不是你的解释

最适合演示的任务：固定重复、步骤明确、没有例外判断的活。比如「每月初导出上月成交，按区域汇总，发到群里」。

最不适合的：涉及判断的。比如「看情况给折扣」——这个没法演示，因为你自己每次判断都不一样。

## 第 7 步：共享给团队

**三种角色（官方文档，2026-10）**

| 角色 | 能干什么 |
|---|---|
| Collaborator | 只能和 Bot 聊天 |
| Manager | 能改它的指令、skills、记忆、插件。所有者和管理者随时能用它 |
| Owner | 只有所有者能删除。删了就全团队没了，不可撤销 |
| 团队管理员 | 能在 Cursor dashboard 的 Manage Shared Bots 里删 |

**什么共享，什么不共享**

这是共享 Bot 最该问清的问题：

| 元素 | 共享 | 私有 |
|---|---|---|
| 插件、密钥、skills、文件 | ✅ |  |
| 团队记忆 | ✅（它会告诉你它记了什么） |  |
| 它记住的关于「你」的事 |  | ✅ |
| 聊天记录 |  | ✅（连所有者和管理者都看不到） |
| 你自己连的账号 |  | ✅（用之前会先问） |

共享的是知识，不是会话。这个切分是整个设计里最聪明的一处。

**分享前必须检查**

分享不产生副本。所以你在分享前配的东西，会在每个同事的聊天里生效。

> 只添加你愿意让所有共享对象使用的密钥和文件。

分享前照这个单子过一遍：插件 ✅ 密钥 ✅ skills ✅ 文件 ✅

## 第 8 步：三条安全边界（不设会出事）

官方文档自己承认的三条，我原样翻译过来，因为它比任何教程都实在：

### 1️⃣ 审批不是硬边界

自动审查（Auto-review，决定一个动作是放行、要审批还是拒绝）「不会审查每一个副作用」——记忆写入和大部分设置变更就是例子。

而且：在没人能应答审批的聊天里，共享 Bot 会绕过自动审查，除非你们团队强制开启（这是企业版设置）。

➡️ 做法：不要靠审批当唯一防线。金额、合同、对外发送，这三类直接在 Skill 里写死「只读」或「不许做」。

### 2️⃣ 提示注入只是被减弱，没被解决

> 官方原话：这些控制「降低但不消除恶意内容的风险」。

一个会读 Slack、邮件、工单的 Bot，读的是团队以外的人写的字。

➡️ 做法：别让 Bot 读没必要的公开渠道；外部内容一律当不可信处理。

### 3️⃣ 共享记忆会把错误一起传播

一条错的事实存进团队记忆，它会出现在每个同事的对话里。

➡️ 做法：指定一个人，每周复查一次团队记忆。不要假设它自己会纠错。

另外两条要记住的：删除是永久的，会连带删掉同事的聊天和 routine；审计日志是企业版专属，Teams 计划没有。

## 抄作业：三个销售 Bot 的配置清单

照着原文的团队配置抄，改成你的：

### Bot A｜客户情报

- **职责一句话**：为我负责的账号做会前准备和会后更新
- **Context**：产品线说明 / 折扣权限表 / 客户档案模板
- **Plugins**：Salesforce、会议记录工具、Slack
- **Routine**：
  - 08:30 每日晨报 → Slack #sales-accounts
  - 「会议结束后」触发 → 更新商机
- **Skills**：Skill 1 会前简报、Skill 2 CRM 更新
- **硬边界**：金额字段只读

### Bot B｜报价助手

- **职责一句话**：根据产品组合和折扣，生成多套报价方案供我对比
- **Context**：产品目录 / 定价规则 / 折扣权限表
- **Plugins**：CRM、报价工具
- **Skills**：Skill 4 折扣前自查
- **硬边界**：绝不代我提交审批；绝不批我自己的折扣

### Bot C｜条款审核

- **职责一句话**：比对非标条款是否符合已批准口径，准备好修改建议
- **Context**：已批准的合同措辞库 / 政策文件
- **Plugins**：合同工具、Slack
- **硬边界**：只出建议，等人批
- **留痕**：每次处理都记下「决策 + 理由 + 支持的负责人」

> 最后那条「留痕」看着不起眼，但它决定了公司敢不敢把活交出去。原文写得很清楚：可追责、可追溯，才符合公司政策。

## 常见坑

| 坑 | 症状 | 解法一句话 |
|---|---|---|
| 职责写太宽 | Bot 什么都干不好 | 一个 Bot 一个岗位，写死范围 |
| 把动态数据写进文件 | 客户信息过期，输出全错 | 从系统实时读，别手维护 |
| 先自动化后固化 | 流程本身不稳定，自动跑得更快更错 | 先做可靠 → 存 Skill → 再上 Routine |
| 晨报硬凑内容 | 每天收到 12 条废话 | Skill 里加「没变化就写无变化」 |
| 密钥用个人凭证 | 全团队在用你的账号 | 只读、最小权限、专用 key |
| 靠审批当防线 | 没人应答时静默放行 | 硬边界写进 Skill |
| 没人管共享记忆 | 一个错事实传遍全团队 | 指定一个人每周复查 |
| 本地 Bot 想共享 | 共享按钮点不了 | 共享 Bot 必须跑云端 |

## 发布前自检

- 职责写成一句话，有范围有边界
- Context 三层都喂了，动态数据没写进文件
- 插件优先，凭证兜底，密钥是只读最小权限
- 每个重复动作都有对应 Skill
- 至少一个 Routine 在跑（从低风险开始）
- 金额 / 合同 / 对外发送，三类硬边界写死了
- 指定了一个人复查共享记忆
- 分享前查了插件、密钥、skills、文件
